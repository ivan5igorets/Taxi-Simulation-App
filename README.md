# Taxi Simulation App

Пет-проект-демонстрация совместной работы **PostGIS** и **TimescaleDB** в одной базе PostgreSQL 16.

Симуляция парка такси в Киеве: машины ездят по реальной дорожной сети (маршруты — OSRM),
клиент вызывает такси, ближайшая свободная машина находится через k-NN-поиск PostGIS
и едет к клиенту по улицам, а вся телеметрия движения пишется в hypertable TimescaleDB
и агрегируется через `time_bucket`.

## Что здесь демонстрируется

| Расширение | Где используется |
|---|---|
| **PostGIS** | `GEOMETRY(Point, 4326)` + GiST-индекс; оператор `<->` (k-NN) для поиска ближайшей машины; `ST_Distance` по `::geography` для расстояния в метрах |
| **TimescaleDB** | `create_hypertable()` для потока телеметрии; `time_bucket('1 minute', …)` для средней скорости за последние 10 минут |

## Стек

- **БД**: PostgreSQL 16 + PostGIS 3.6 + TimescaleDB 2.28 (Docker)
- **Бекенд**: Node.js + TypeScript + Fastify + `pg`
- **Фронтенд**: Vue 3 (Composition API) + Vite + Leaflet + Tailwind CSS
- **Маршрутизация**: публичный демо-сервер [OSRM](http://router.project-osrm.org/)
  (`router.project-osrm.org`) — реальные пути по дорогам вместо движения по прямой

## Запуск

Нужны Docker и Node.js 20+.

```bash
# 1. База
docker compose up -d

# 2. Бекенд (порт 3100)
cd backend
cp .env.example .env
npm install
npm run dev

# 3. Фронтенд (порт 5173) — в отдельном терминале
cd frontend
npm install
npm run dev
```

Открыть http://localhost:5173

> **О портах.** БД слушает **5433**, а бекенд — **3100** (стандартные 5432 и 3000
> заняты другими проектами на машине разработчика). Меняются в `docker-compose.yml`,
> `backend/.env` и `frontend/vite.config.ts`.

## Как пользоваться

- При загрузке генерируется случайная точка клиента (зелёный маркер) и парк из 3–10 машин,
  прижатых к ближайшим дорогам (OSRM `/nearest`).
- **«Вызвать такси»** — запускает случайный таймер 5–50 с («Ищем ближайшего водителя…»),
  после чего идёт запрос на бекенд; назначенная машина подсвечивается синим, на карте
  рисуется реальный маршрут по улицам (OSRM `/route`), и машина едет по нему —
  пройденная часть пути тускнеет, остаток остаётся ярким.
- **«Перезапустить мир»** — полный сброс БД и генерация нового парка.
- Нижняя панель показывает остаток пути **по дороге** (`ST_LineSubstring` от текущего
  прогресса такси до конца маршрута), среднюю скорость (`time_bucket`) и сам SQL
  по кнопке «показать SQL».

Цвета маркеров: 🟢 клиент · 🟡 свободно (`IDLE`) · 🔵 в пути (`ON_THE_WAY`).

> **OSRM — чужая инфраструктура без SLA.** Если демо-сервер недоступен или отвечает
> с ошибкой, приложение не падает: заказ создаётся без маршрута (`route: null`),
> карта рисует пунктирную прямую линию (как раньше), а такси едет к клиенту
> «стрелкой». Это фолбэк, а не баг — симуляция работает и без интернета.

## API

| Метод | Путь | Описание |
|---|---|---|
| `GET` | `/api/taxis` | Все машины с текущими координатами |
| `POST` | `/api/orders` | Создать заказ `{lat, lon}`; назначает ближайшее свободное такси, запрашивает маршрут OSRM (409 — нет машин) |
| `GET` | `/api/orders/:id` | Состояние заказа, геометрия маршрута и остаток пути по дороге |
| `GET` | `/api/telemetry/stats/:taxiId` | Агрегация `time_bucket` за 10 минут |
| `GET` | `/api/telemetry/summary` | Объём hypertable по всему парку |
| `POST` | `/api/reset` | Очистка мира и генерация нового парка |
| `GET` | `/api/health` | Проверка связи с БД + состояние воркера (`running`, `idleForMs`); не будит воркер |

Любой другой `/api/*` запрос будит воркер симуляции, если он спал (см. «Автостоп воркера» ниже).

### Воркер и движение по дорогам

Тикает раз в 5 секунд. У каждой машины может быть сохранённый маршрут
(`taxis.route` — `LineString`, результат OSRM `/route`):

- **Есть маршрут** — воркер не считает координаты сам. Он продвигает
  `route_progress_m` на пройденные метры за тик, а точку на дороге выдаёт сам PostGIS:
  `ST_LineInterpolatePoint(route, progress_m / ST_Length(route::geography))`.
  Машина физически не может оказаться вне сохранённой линии.
- **Маршрута нет** (OSRM ещё не ответил или недоступен) — фолбэк на прежнее поведение:
  `IDLE` блуждает случайно (разворот к центру за радиусом города), `ON_THE_WAY` —
  шаг по прямой к клиенту (`stepToward`).
- `IDLE`-машины без маршрута периодически получают новый «патрульный» путь до
  случайной точки города — не больше `osrm.maxRouteRequestsPerTick` (2) новых
  запросов к OSRM за тик, чтобы не заваливать чужой демо-сервер разом при старте
  с большим парком.
- Доехала до конца линии (`route_progress_m >= длина маршрута`) → заказ `COMPLETED`,
  такси `IDLE`, `route` очищается.

За тик выполняется один батч-`UPDATE` парка и один батч-`INSERT` телеметрии
(раздельно для машин с маршрутом и без — разная формула позиции).

Таймер воркера — единственный на процесс: `startWorker()` всегда сначала вызывает
`stopWorker()`, поэтому повторные `/api/reset` не плодят параллельные воркеры.

### Автостоп воркера

Воркер не запускается при старте сервера — только по первому `/api/*` запросу
пользователя (`noteActivity()` в `onRequest`-хуке `server.ts`). Если 10 минут
(`WORKER_IDLE_TIMEOUT_MS`) не было ни одного запроса — воркер сам себя останавливает
на очередном тике и перестаёт писать в hypertable. Любой следующий `/api/*` запрос
(кроме `/api/health` — иначе внешний мониторинг держал бы симуляцию вечно живой)
будит его заново.

Пока вкладка браузера открыта, `useTaxis` опрашивает `/api/taxis` каждые 2 с,
поэтому воркер не уснёт, пока приложение открыто, — заснёт только после закрытия
вкладки или простоя без единого запроса.

### OSRM и отказоустойчивость

`services/osrm.ts` оборачивает `router.project-osrm.org` — публичный демо-сервер
без SLA. Любой сетевой сбой или таймаут (3 с) возвращает `null`, а не бросает
исключение; после 3 сбоев подряд открывается circuit breaker на 60 с, чтобы не
долбить упавший сервис на каждом тике. Ни один из потребителей (`worker.ts`,
`simulation.ts`, `routes/orders.ts`) не считает `null` ошибкой — везде есть путь
без OSRM.

Переопределить адрес (свой инстанс OSRM или заглушка для тестов) — `OSRM_BASE_URL`
в `.env`.

## Заметки по реализации

- **Блокировка при назначении.** k-NN-запрос и `FOR UPDATE` разделены: блокировать
  строки прямо в запросе с `ORDER BY <-> … LIMIT 1` нельзя — параллельный воркер
  обновляет те же строки, и index scan падает с `attempted to lock invisible tuple`.
  Поэтому берутся 5 кандидатов по индексу, а затем отдельным запросом блокируется
  первый ещё свободный (`FOR UPDATE SKIP LOCKED`).
- **`taxi_telemetry` без FK на `taxis`** — внешний ключ заблокировал бы `TRUNCATE`
  в `/api/reset`; связь логическая.
- **Числа из `pg`.** `FLOAT8`/`NUMERIC`/`INT8` парсятся в `number`, иначе координаты
  и скорости уезжают в JSON строками.
- **Маршрут запрашивается после `COMMIT`, а не внутри транзакции назначения.**
  Сетевой вызов к OSRM не должен держать открытым соединение и блокировку строки
  такси — заказ создаётся сразу, `route` дописывается отдельным `UPDATE` следом.
- **`orders.route` — снимок, `taxis.route` — живое состояние.** Когда такси доезжает,
  `taxis.route` обнуляется для следующей поездки, а `orders.route` остаётся
  навсегда — иначе `GET /api/orders/:id` для завершённого заказа потерял бы
  геометрию маршрута.
